## Shared owner rules — 31 October 2026

At the beginning of every new project/chat, read [GENERAL_RULES.md](GENERAL_RULES.md) and the current [general-rules repository](https://github.com/Superaids/general-rules) (START_HERE, README, AGENTS and linked policies) once when authenticated access is available. Fetch once and read the fetched revision; tools/start-project.py can do this without resetting local edits. Use the checked-in snapshot if unavailable, then read this project's current handover and instructions.

These instructions apply on every device and travel with the repository. When creating a new project/repository, install this portable startup pointer, GENERAL_RULES.md and GAME_DEV_GUIDE.md using the canonical tools/bootstrap-project.py or equivalent file writes before implementation and first push. A machine-local rules checkout is only a cache.

Quality bar: elevate concepts and "Blizzardify" games. Ask: **"Would peak Blizzard really be ok with this quality, or how would they make it more compact, easily understandable with amazing game feel?"** Judge actual play, clarity, accessibility, compactness, craft and enjoyment; tests alone do not establish quality or acceptance.

Game feel and purposeful juiciness are among our highest priorities from the first playable prototype. Make core actions responsive, tactile and satisfying to repeat through coordinated controls, timing, animation, sound, haptics and effects. Tune juice for clarity and enjoyment, with appropriate accessibility and performance; more effects alone do not establish quality. Apply responsive, satisfying feedback to other interactive projects as appropriate.

For game work read the canonical game-dev-bible core (00, 01, 02), then relevant topics through its READING-MAP.md; use GAME_DEV_GUIDE.md offline. Agents own craft preparation and evidence-backed decisions; the owner should not teach basic game design. Generic flat SaaS/web UI is not an adequate default game interface. Apply coherent game art, hierarchy, desirable objects and complete responsive states. No reading or test guarantees studio-equivalent quality.

Protect work marked done/accepted/completed from direct or indirect changes without specific owner authorization. Check completed dependencies affected by new work, including tutorials when adding units. Near production completion the owner may explicitly activate controlled review; a chat may suggest it with reasons. Once activated, maintain all current old/new reviews, frame-by-frame/game-speed sprite playback, comments, Approve, Send back with notes and a prioritized To do/In progress/In review/Approved to prod board. Use versioned approvals and tested delivery/resume to the working chat; approval is distinct from production verification. Do not impose this on new projects by default.

Every purchase/ad should feel happy and worthwhile, never scammed. Sole later owner exception: very simple games primarily funded by ads plus no-ads may use forced ads to encourage no-ads, based on current research and game-specific retention/churn/satisfaction/net-value evidence; rewarded value is preferred. This narrowly supersedes older blanket forced-ad bans. Read canonical Bible chapter 35.

Maximize useful lawful anonymous insight through Sjouheim Pulse (Bible chapter 36 and its current integration/API/review). Preserve aggregate/permission boundaries; sessions do not establish unique players/retention or verified revenue. Hashes/IDs and small aggregates are not automatically anonymous. Choose supported lawful bases/exemptions without unnecessary restrictions; consent where required, honest privacy, no selling player data/covert cross-game tracking.

The owner does not pay for GitHub; included Actions usage is scarce. Use local checks. No automatic hosted triggers without a later explicit, scoped owner exception. Useful manual cloud/native checks need owner authorization and a stated usage bound. Do not upgrade billing, change visibility, repeatedly poll CI or push status receipts for an unchanged hosted block. Keep meaningful tests and player-satisfaction monetization rules. This instruction supersedes older after-every-push CI requirements; unrelated stops, approval, privacy and save rules remain in force. Policy 2026-10-31.4.
