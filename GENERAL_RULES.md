# Shared owner rules

Policy version: 2026-10-31.2. Adopted 31 October 2026. Canonical source: https://github.com/Superaids/general-rules.

## Read at the start of every project/chat

Read this snapshot and the current general-rules README, AGENTS.md and linked quality, Actions and working-agreement documents once at startup when authenticated access is available. Then read this project's own instructions, handover and relevant owner feedback. A cached authenticated Git checkout can be fetched without resetting local files. If access is unavailable, use this snapshot, identify its version and continue independent authorized work. Do not poll the rules during a task or store credentials in Git.

These rules travel in Git and apply on every device, not only a particular computer. When a chat creates a new project/repository, it must install the portable root AGENTS.md pointer and this GENERAL_RULES.md snapshot before implementation and its first push. Use the canonical repository's tools/bootstrap-project.py or equivalent authenticated file writes while preserving existing instructions. A local rules checkout is only a cache. GitHub account membership does not automatically populate a new empty repository; the creating chat must perform this bootstrap.

Latest explicit human instructions govern conflicts. These owner rules supersede older requirements to run/check hosted CI after every push. Preserve all unrelated project stops, approval boundaries, privacy and save compatibility. General quality guidance does not reopen a stopped project or approve unseen art changes.

## Elevate concepts: the peak Blizzard standard

> We are here to elevate concepts to new heights. We are here to "Blizzardify" games. Just like Blizzard at their peak took existing genres and ideas and immensely heightened the quality, accessibility for the masses, game feel and enjoyment from playing like they did with WoW, WarCraft, StarCraft, Overwatch, we are here to take concepts to wild new heights of quality and player satisfaction.
>
> We will measure everything against: "Would peak Blizzard really be ok with this quality, or how would they make it more compact, easily understandable with amazing game feel?" and strive towards those heights.

Evaluate the actual playable journey: the appeal of the core activity; an immediately recognizable goal/action/state/consequence; compact, purposeful controls; broad accessibility; responsive touch/motion/sound/feedback; coherent art and interface; meaningful depth; and enjoyable progression. Teach through play. Remove unnecessary screens, repetition and administrative effort while preserving depth. Review real entry, onboarding, core actions, results and save return on the intended screen/input. Passing tests, recolors, static cards and a feature list do not certify game quality, fun or owner acceptance. Respect the project's approved direction and make concrete improvements within authorized scope.

## Scarce GitHub Actions usage

The owner does not pay for GitHub and included Actions usage is limited. Local checks are the default. Do not add automatic push, pull-request, schedule, chained or other hosted triggers without a later explicit, scoped owner exception. Repositories without a demonstrated Actions purpose keep Actions disabled. Retain useful manual clean-checkout/native checks only; dispatch them only within owner authorization with a stated purpose, platform, expected jobs/runtime and short artifact retention. A manual workflow's existence is not permission to run it.

Keep meaningful tests, lockfiles, native sources and local validation tools. Preserve specialist suites and complete regression/evidence assembly where required. Do not weaken assertions to obtain green checks. Do not trigger CI for documentation/status receipts, routine backups or repeated full suites that inform no decision. Do not repeatedly poll or push merely to record an unchanged hosted startup block. A billing-rejected job has no test verdict. Report the limitation once and continue independent local work. Never upgrade billing, use paid runners, change spending limits or expose a private repository to get more usage without explicit owner authorization.

## Player satisfaction and monetization

Monetization must never hurt player satisfaction. Every purchase, advertisement or other monetization interaction must be designed and evaluated to make the player happy, feel worthwhile and make them want to repeat it. Add desirable value to an enjoyable free game. Do not manufacture frustration, shortages, illness, neglect, delays or other pain to sell relief. Do not interrupt play with unwanted ads or penalize declining. Show exact value and price before commitment; avoid guilt, deceptive offers and pressure. Evaluate enjoyment, regret and the free-player experience alongside revenue; revise or remove harmful monetization. No design guarantees that every person will enjoy every offer without actual validation.

## Working agreements

Preserve substantive progress in final responses: what changed, why, what was checked, honest limits and pending work, then outcome/next work. Keep durable handover and owner decisions in Git. Complete authorized work without claiming user acceptance, game completion, deployment or tests that did not occur. Preserve approved art, working features, player progress and unrelated local changes. Follow the project's source/mirror publishing process; fetch and integrate current remote work without force-pushing. Keep these rule files in generated mirrors. Policy/documentation changes do not require deploying unchanged applications or spending cloud CI usage. Keep secrets, sessions, signing keys, installed dependencies and disposable caches out of Git. Keep private repositories private. Reuse one current game browser tab, close obsolete task tabs and preserve unrelated active work.
